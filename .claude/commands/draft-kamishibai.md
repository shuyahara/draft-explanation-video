## 0. 企画確定と構成メモ（ユーザーの確認はここまで）

0. **企画確定（`grilling` スキル併用）**: ①結論の方向 ②構成型（論証型／探索型） ③トーン
   ④切り口。調査で分かることは聞かない。
   - **尺は時間から決めない**（2026-09-13 ユーザー指示）。先に「何分の動画にするか」を決めて、それに
     合わせて内容を足したり削ったりしない。**議論として優れた構成になるか**（主軸の ABT が一文で通るか、
     根拠が足りているか、有力な反論に答えているか）だけで必要な章を決め、尺はその結果として出た長さを
     受け入れる。したがって企画確定の段階で想定尺は聞かない。構成メモで章立てが固まってから概算文字数を
     計算して記載する（日本語 TTS で約 300〜360 字/分。話速 1.1 ならその 1.1 倍が目安）。
     章を削るのは「主題に寄与しないから」であって「長いから」ではない。
   - **主題の語を一つに決める**（2026-09-12）。タイトルに使う語（例: 「誠実な」）と、本編で定義する語を
     一致させる。「まとも」を定義してから「優しさ」の話を始める、のように語をすり替えると論理が飛ぶ。
     定義は「悪いことをしない」のような消極条件でなく、具体行動（嘘をつかない・約束を守る・逃げない）で言う。
   - **区分・段階の名前は日常語**（「①会う前 ②初対面 ③長い関係」。「会ったあと」「続いてから」は抽象的）。
   - **ずんだもんの性別**: 本来は女の子の設定。男性の当事者として語らせる企画は、冒頭 1 枚目の
     クレジット欄に小さく「※本動画ではずんだもんは男の子という設定です」を出す（ユーザー指示 2026-09-12）。
0.5. **構成メモで合意を取る**: `templates/kousei-memo-template.md` の書式で書く。**先頭に「要約版の本文」**
   （章ごとに 3〜6 文の地の文、決め文は「」、章末にずんだもんの問い。800〜1,200 字）を置き、ユーザーが
   流し読みで主軸と流れを確認できるようにする（2026-09-13 指示）。主軸は ABT の一文、冒頭は SCQA、
   末尾の点検表（docs/structure-references.md §4: デイマーの 5 基準・トゥールミンの限定と反証・
   ミントの SCQA・オルソンの ABT・覆る常識の予告）を自分で通してから提示する。以降はレビューと
   自分の点検で仕上げ、試写に出すのは一度で済む状態にする（2026-09-06 指示）。

## 1. 調査と裏取り

- 引用は一次資料で確認し、数値は「本文 p.X／Table N」の所在つきで `references/` に残す。図からの読み取り値・
  要旨や二次記事の数値は採用しない（Greitemeyer の誤値、2026-09-11）。**本文が取得できない研究は数値を
  載せない**（Back 2010 / Leckelt 2015、2026-09-12）。
- 相関などの数値は、動画の問いの向き（例: 女性が男性を評価した側）で採る（Eastwick 2008 の取り違え、2026-09-11）。
- 研究者の肩書きは一次資料で確認できたものだけ言う。日本の大学院生は無名（docs/dialogue-guide.md §7）。
- 「石器時代から脳は変わっていない」のような通説は、当たっている部分と言い過ぎの部分を分けて答える。

## 2. 執筆（docs/dialogue-guide.md §1〜§5・§7・§8）

- 1 行 = 1 発話 `**話者**（表情）: 本文`。1 キューは 50 字以内。各シーン 1,000 字以内。
- **簡潔で直接的に**（2026-09-12「面白さを履き違えている」）: 比喩・婉曲・言い換えを使わず一文一義。
  抽象動詞（効く・向かう・用意する）は具体語（有利に働く・効果が出る・何度か会う機会を作る）に。
  反転は説明の言葉で言い、対句の型を雛形にしない。指示語（三つ目・後の方・その時間）は名詞で言う。
- **結論は早く、その後の視聴理由を作る**: S2 で答えを早く出し、覆る常識を 3 つ用意する。**予告・限定・「ここからは推論」
  などの骨組みを台詞で宣言しない**（docs/dialogue-guide.md §9。構成メモの点検表で満たし、台詞は場面の言葉で）。
  対句・決め台詞の型、読点刻み、理論名の先出し、ずんだもんの主語のない要約も §9 の禁止リスト。
- 主題から遠い研究は削る（10 分あたり 5〜6 本まで。起源・歴史の章は主題に必要な一点だけ）。
- **研究の限定・ネガティブ情報は、反証の反証を用意する章だけで言う**（docs/dialogue-guide.md §10。結論が変わらない限定は本編で言わず概要欄へ）。逸話の固有情報を全編に引きずらない、ギャグを作らない、フックで枠組みを言わない、セクション名は中立、も §10。
- 結びは行動の転換＋めたんの励まし（「頑張って、ずんだもん」）で閉じる。末尾の挨拶は本編に書かない（終了カードが担う）。
- タイトル末尾に必ず `【ずんだもん&めたん|ゆっくり解説】`（§6）。

## 3. レビュー一式（試写前に全部回す）

`review_script.py`（7 観点）→ `review_holistic.py`（総合）→ `review_clarity.py`（理解度・説明の抜け・主題適合・
直接表現・**冗長／婉曲・構成の切れ味**）→ `review_dialogue.py`（セリフ）→ `review_ai_tone.py`（AI らしさ。台詞が文書になっていないか）→ `review_transitions.py`（つなぎ）→
YAML 生成後に `review_pauses.py`（間）。`review_script` / `review_holistic` は対話形式を読めないので
`**ナレーション**` 形式に変換してから渡す（`tools/review/README.md`）。採否と根拠を Issue に残す。
GPT が拾えないもの（冒頭の例が論の前提と合うか、反転の否定範囲、研究の帰属の向き）は自分で点検する。

## 4. YAML・素材・検証

1. `tools/kamishibai_md_to_yaml.py <md> --bgm ../bgm/<曲>.mp3 --bgm-credit "..." --puppet-sink 0.12 --tempo 1.1`
   で YAML を生成し、`scripts/<動画>/apply_beats.py`（アンカー文字列でビート・図解・板・読みを流し込む。
   毎回 YAML を再生成してから適用）→ `stage_assets.py`（候補フォルダから `render-assets-<動画>` へ配置）。
   - **ユーザーが GitHub 上で台本を編集中は push しない**。取り込み後は `anchor not found` を全部直す
     （アンカーはキュー＝文単位。「ええ。」のような短文は別キュー）。
   - 道しるべの板（三つの段階など）は各章頭に同じ板を出し、**その章の行を `highlight_lines` で金色に**する
     （「← いまここ」は書かない。2026-09-12）。章カードは 5 枚まで（validate の上限）。
   - 図解の主役の数字は一つに絞る（68%・22 か月・70% を並べると主役が定まらない）。
2. `validate`（OK・警告 0）→ `tools/preflight.py --assets-dir <render-assets>`（読みの突合・50 字超・板 10 秒超・
   要確認文字・ラベル長・写真の有無。辞書側ノイズ〔年→とし 等〕は VOICEVOX の audio_query で読みを確かめて無視）。
   - **読みの確認は Python から UTF-8 明示で `audio_query` を叩く**（`urllib.parse.urlencode(..., encoding="utf-8")`）。
     Git Bash の curl で日本語を送ると文字コードが化け、「こんにちは」が空・「天気」が「ブイ、シイ」のように
     エンジンが壊れて見える（2026-09-17。辞書を退避してしまったが無関係だった）。エンジンや辞書を疑う前に、
     無関係な短文で送信経路を切り分ける。辞書の重複登録（同じ語が 22 重）は tts.py 側で修正済み。
3. `storyboard` で全ビートを出し、自分で見る（`/draft` 仕上げ手順 3 の点検項目＋ docs/dialogue-guide.md §6 の板の規則）。
   写真の並び（「縮こまった姿勢」の台詞に開いた姿勢の写真、など）と看板の文字も見る。
4. **ビート適合表を作って場面と画を突き合わせる**（2026-09-16 試写指摘「場面に合わない写真がところどころ」）。
   `storyboard.md` の表に「そのビート中に読まれる台詞の要旨」の列を足し、ビートごとに ○△×を付ける
   （`references/<日付>-<動画>-image-audit.md`）。絵コンテを眺めるだけでは台詞との食い違いを見落とす。
   - **研究の紹介ビートには、その研究のイメージ（誰に・何をして・何が分かったか）を図解か画像で必ず出す**。
     MRI 装置・表彰台・教室のような「場所の写真」は導入にはなるが研究の画の代わりにはならない。
     図解なら `sketch`（誰に→何をした→結果の格子。裏取り済みの数字だけ）、画像なら実験の場面を
     直接描写した Codex 生成（docs/asset-workflow.md。「実験で参加者が写真を見比べている」のような
     説明的な情景はストックでは出てこない）。ストック優先の原則は研究の画には適用しない。
   - ×と△は差し替えてから preflight・storyboard をやり直す。

## 5. レンダと検証

```
cd C:\Users\shuya\Projects\script-to-video
.venv\Scripts\python.exe -m script_to_video render <yaml> ^
    --out-dir D:\script-to-video-build\<動画>-vN ^
    --assets-dir C:\Users\shuya\Projects\assets-kamishibai\render-assets-<動画> ^
    --tts-backend voicevox --tts-rate 1.1 --outro-seconds 8 ^
    --end-card C:\Users\shuya\Projects\assets-kamishibai\endcard\endcard.mp4 ^
    --name <動画>-vN
```

- **`--end-card` は必須**（15 秒の終了カード。誠実な男性版で 4 版付け忘れた、2026-09-13）。付け忘れた mp4 には
  `script_to_video.endcard.append_end_card(video_path, end_card_path)` で後付けできる（in-place なので先にコピー）。
- VOICEVOX は `vv-engine\run.exe` を先に起動。レンダは 20 分前後かかるので PowerShell の `Start-Process`
  で切り離し、`render.log` の `RENDER_EXIT=` を監視する（Bash の背景実行は 10 分で切れる）。
- 完了判定はプロセス終了。検証は ①尺 ②冒頭 20 秒の max_volume（BGM あり） ③末尾 10 秒の音量と最終フレーム
  （終了カード）④ 差し替えた写真の箇所のフレーム。
- レンダ後: `review_video.py` ＋ `review_reading.py`（ASR。要確認は VOICEVOX の kana で判定）→ 直して再レンダ
  （自分の判断で 2 回まで）。

## 6. 公開パッケージ

- 概要欄 `description-v1.txt`（`__CHAPTERS__` を `fill_chapters.py` で埋めて v2）、`tags.txt`、`upload-record.md`。

  文字は描かない）。人物は画面中央・腰から上。**金色の大きな「？」を人物に重ねてよい**（目は隠さない）。
  文字帯は上下とも**全幅**（上: 問い、下: 副題）。めたん・ずんだもんは**下端から顔が覗く大きさ**で左右に。
  3 案を作ってユーザーが選ぶ。差し替えは `thumbnails().set` で再アップロード不要。
- 非公開アップロード（`--thumbnail --srt --token secrets/youtube_token_kamishibai.json`）→ 処理完了を確認 →
  旧版を削除（`videos.delete`、private のみ）→ 記録・Issue・メモリを更新。
