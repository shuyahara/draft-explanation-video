# Design: script-to-video（台本→機械音声解説動画 生成ツール）

## Overview

自分専用のローカル完結パイプライン。設計の核は「**執筆時に確定・実行時は決定的・承認は人**」
の三段分離である。判断が必要な情報（検索クエリ・素材候補・ライセンス・読み・BGM）はすべて
台本執筆時に Claude が確定させてシーン YAML に書き込み、ツール本体は LLM を呼ばない
決定的なバッチ処理に徹する。人の関与はレンダリング前の候補ギャラリーでの承認操作のみ。

## Architecture

```
[執筆レイヤー（Claude Code・台本リポジトリ側）]
  台本 Markdown（人間用マスター）
  シーン YAML（レンダリング指示書）
    ├ ナレーション本文 / テロップ / 読み修正 / ポーズ秒数
    ├ 素材候補 URL（画像・動画クリップ）2〜4件 + ライセンス情報 + 出典表記（執筆時に検索・下調べ済み）
    ├ 生成プロンプト（シーン別）+ スタイル定義（全体で1箇所）
    └ BGM 指定（候補選定・ライセンス確認済み、ファイルはユーザーが配置）
        │
        ▼
[ツール本体（ローカル CLI + ローカル Web UI）]
  1. Loader      … YAML 読み込み・検証（欠落/形式エラーをシーン単位で報告）
  2. Gallery     … 候補ギャラリー（ブラウザ）: ライセンスバッジ表示、選択、
                   動画候補のプレビュー再生、再検索（ストック/Commons/汎用）、
                   生成AI実行（明示操作のみ）。採用素材は即ダウンロードして中間素材へ保存
  3. TTS         … VOICEVOX エンジン（ローカル）でシーン別 WAV 生成。
                   読み修正・ポーズ挿入を反映
  4. Renderer    … ffmpeg でシーン合成: 背景+見出し+テロップ+採用素材、
                   静止画に Ken Burns、動画素材は尺合わせ（トリム/ループ）+音声ミュート、
                   出典テロップ、SRT 生成
  5. AudioMixer  … BGM ループ、-14 LUFS 正規化、ダッキング
  6. Packager    … 完成 MP4 + 中間素材（WAV/PNG/SRT/タイムライン）を構造化保存
        │
        ▼
  出力フォルダ（MP4 + 中間素材一式 → 必要時のみ AviUtl 等で再編集）
```

外部通信は「素材検索 API（Pixabay / Pexels / Wikimedia Commons / 汎用画像検索）・
画像ダウンロード・画像生成 API」のみ。パイプラインの実行順は
Loader → Gallery（人の承認で確定）→ TTS → Renderer → AudioMixer → Packager。
ギャラリーでの選択結果は YAML と別の選択記録ファイルに保存し、再レンダリング時は
承認をスキップできる。

## 設計判断

| 論点 | 決定 | 理由 | 却下した代替案 |
|---|---|---|---|
| 対象ユーザー | 自分専用ツール | 確実に存在する課題は自分の HeyGen 手動運用の手間。最小で作り価値を検証 | 他者提供 SaaS／将来製品化前提の設計（「将来のため」の抽象化は初版を重くする） |
| レンダリングエンジン | 自前パイプライン（VOICEVOX 系 + ffmpeg） | 手動作業ゼロを無料で達成。アバターは不要と判断 | HeyGen API（従量課金が量産と相性悪い）／HeyGen 手動維持+周辺自動化（手動が残る） |
| 出力形式 | 完成 MP4 + 中間素材一式 | 基本は全自動、直したい時だけ素材から編集。中間素材保存はレンダの副産物でほぼ追加コストゼロ | MP4 のみ（後編集不能）／AviUtl .exo 直接生成（独自形式でコスト高、B の素材から後付け可能） |
| 映像トラック | テロップ+背景+見出し自動、素材はシーン単位で配置 | 生成コストと品質リスクを人の承認で制御 | 完全自動ビジュアル生成（品質不安定・コスト・手直し発生の三重苦） |
| 素材採用フロー | 候補ギャラリーで人が選ぶ（初期候補は執筆時収集） | 審美判断はどのみち人に残る。レンダ前選択が手戻り最小。生成 API 課金も承認制になる | 完全自動採用（クエリ精度に品質が引きずられる）／全自動ドラフト→差し替え（レンダ2回で遅い）— どちらも将来拡張として保留 |
| ライセンス方針 | 収益化前提。ストックは商用可・クレジット不要源（Pixabay / Pexels）に限定 | 最初から絞るコストはゼロ。遡及確認・差し替えは高コスト | 非商用前提の広いソース選択（後から収益化する時に破綻） |
| 実在・固有名詞素材 | Wikimedia Commons 主 + 汎用画像検索併用。権利不明画像は出典記録+出典テロップ必須（引用要件対応） | 偉人肖像はほぼ PD で Commons に揃い、ライセンスが機械可読。汎用検索は「解説に必要な画像を適宜」の要件に必要で、権利判断は人が負う | Commons のみ（対象が人物以外に広がると不足）／汎用検索のみ（収益化と正面衝突） |
| 入力フォーマット | シーン YAML（レンダリング指示書）を新設、台本 Markdown と二層 | 判断を執筆時に確定させ、ツールを LLM 非依存の決定的処理にする | 台本 Markdown 直接パース（実行時 LLM 推定が必要）／HeyGen CSV 拡張（入れ子構造に弱い） |
| 生成 AI | 画像生成のみ・クラウド API。静止画 + Ken Burns で動きを補う | 解説動画の体感品質は静止画+ズームパンで十分。スタイル統一は共通スタイル定義+シーン別プロンプト連結 | 動画生成 API（コスト一桁上、将来拡張へ）／ローカル SD 系（GPU 要件とチューニングの手間が趣旨に逆行） |
| ストック動画素材 | Pexels / Pixabay の動画クリップもシーン素材に含める（生成 AI は静止画のみのまま） | 画像と同一 API・同一ライセンスで候補収集・承認への追加コストがほぼゼロ。動きのあるインサートで表現の幅を確保。尺合わせ・ミュートは ffmpeg の定型処理 | 画像のみ（Ken Burns 代替では表現の幅が一段落ちる）／将来拡張へ保留（元要望に含まれており先送りの理由がない） |
| 素材選定の前倒し | 執筆時に Claude が候補収集+権利下調べ、最終選択は人 | 価値が大きいのは権利の下調べで、台本の裏取りと同一セッションが自然。全素材（ストック/実在/生成/ BGM）が同一パターンに統一される | 執筆時はクエリのみ（権利確認が実行時に残る）／執筆時に1枚に決定（人の目が入らない） |
| 実行環境 | 完全ローカル（CLI + ローカル Web UI） | 自分専用・承認工程あり・TTS ローカル無料の帰結で、クラウドに置く動機がない | クラウドデプロイ（費用と運用が純増）／ハイブリッド（レンダ速度が問題化した時の将来拡張で足りる） |
| BGM | 執筆時に候補選定（ライセンス込み）、ツールはループ・-14 LUFS・ダッキングの自動ミキシング | 選曲は定番曲の使い回しで足り、価値はミキシング自動化にある。実行時は ffmpeg の決定的処理 | BGM なし（長尺で聴き疲れ、毎回 AviUtl 行き）／実行時自動選曲（価値薄、DOVA 等は API なし） |

## Open Questions

- VOICEVOX の話者選定とクレジット表記（「VOICEVOX:話者名」）の挿入方法（エンドクレジット自動挿入を想定）
- 解像度・アスペクト比（1080p / 16:9 を既定と仮置き）
- 技術スタック（言語・フレームワーク）の選定
- ツール本体のリポジトリ配置と本スペックの移設タイミング
- 画像生成 API のプロバイダ選定（商用利用条件の確認込み）
- ダッキングの実装方式（ffmpeg sidechaincompress を想定、パラメータは実測で調整）
- 将来拡張（対象外）: 完全自動モード／全自動ドラフト→部分差し替え、動画生成 API、.exo 出力、クラウドレンダリング
